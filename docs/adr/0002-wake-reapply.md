# 0002 — 系统唤醒后重应用当前杯态

- **状态**：Accepted（2026-11-18）
- **日期**：2026-11-18
- **决策者**：fb0sh（委托 Agent 定夺）
- **关联**：Issue #10、ADR-0001

## 背景

TriCup 的三态是进程内存状态，合盖/开盖不会重置，图标在开盖后仍显示原状态。但空杯/半杯合盖会真正睡眠、进程被挂起；唤醒后 IOKit 断言通常由系统保留，却不存在显式保证。用户明确期望"合盖再开盖后继续按之前的逻辑生效"，主流防休眠工具也是如此（运行期间保持状态、唤醒后继续生效）。

## 决策

当系统从睡眠唤醒后，主动、幂等地重新应用**当前**杯态（不改变用户选择，不自动切换状态）：

1. App 监听 `NSWorkspace.didWakeNotification`（主线程）。
2. 调用 `SystemPowerManager.reassertCurrentState()`：
   - `.empty`：释放全部断言（无租约）。
   - `.half`：重新申请"系统 + 显示器"断言。
   - `.full`：若 Helper 报告租约有效 → 重新申请断言（**不重复建立租约**）；若 Helper 不可达或租约已失效 → 走既有断连降级（降为空杯并提示，**不自动重新申请满杯**）。
3. 唤醒后立即评估一次低电量策略（睡眠期间掉到 ≤15% 时按策略降空杯）。
4. 若重应用后仍无法确认 `SleepDisabled` 或检测到外部 `SleepDisabled=1`，保持既有"不确定/外部阻止"提示，不谎称允许休眠。

幂等性：重复调用不产生副作用；`.full` 不会因重应用而自动开启新租约。

## 理由

- 与主流防休眠工具的"运行期间保持状态、唤醒后继续生效"一致，符合用户直觉。
- 仅补"唤醒后重应用"，不改变三态语义、不加新状态/设置，KISS。
- 失败时沿用既有断连降级与手动恢复提示，不静默重试，避免把 Mac 重新钉醒。

## 影响与残余风险

- 监听唤醒事件是 AppKit 常规能力，无新增权限。
- 若唤醒后 Helper 恰好不可达，会降为空杯并提示（与现有断连处理一致），而非静默恢复满杯。
- 低电量在睡眠期间变化会在唤醒后立即生效，属预期安全行为。
- 该行为仍受 `pmset`/Helper 的既有全局设置与恢复风险约束（见 ADR-0001）。

## 备选方案

- **不处理唤醒**：依赖系统保留断言；不可靠，且与用户预期不符 → 否决。
- **唤醒时自动重新申请满杯**：若 Helper 恰好断连会造成"静默重试/反复唤醒"，违背安全策略 → 否决。
- **唤醒后重置为空杯**：与用户预期相反，且会意外改变用户选择 → 否决。

## 验收

- M4 Air：半杯合盖→开盖后仍为半杯且断言继续生效；满杯合盖（不睡）开盖后仍满杯；满杯时若 Helper 已断连，开盖后降为空杯并提示、不自动重开。
- 单测：`reassertCurrentState()` 的 empty/half/full/lease-lost 分支；不重复申请租约。
